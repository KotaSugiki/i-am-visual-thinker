# システムフローの説明例

以下は架空の教材用仕様。対象プロジェクトの実装だと扱わず、実際には読み取ったコードと条件に置き換える。

## 注文受付からバックグラウンド処理まで

教材の仕様：`createOrder` は認証し、注文を保存し、配送ジョブを登録して受付応答を返す。保存に失敗すれば登録しない。`processOrder` は登録したジョブを受け取り、配送APIを呼び、完了を保存する。応答とワーカー完了の前後関係、配送APIの内部、再試行は未指定。

全体図ではAPIとワーカーを別の領域に配置する。

- API：リクエスト → 認証 → 注文保存 → ジョブ登録 → 受付応答。
- ワーカー：登録済みジョブ → ジョブ受信 → 配送API → 完了保存。
- 分岐：認証失敗ならエラー応答へ。保存失敗ならジョブ登録へ進まない。

「登録したから配送完了」「受付応答の後に必ずワーカーが動く」というアニメーションにはしない。全体の段階送りは説明順であり、観測した時間順とは区別する。並行部分は別レーンで示し、順序未指定の注記を近くに置く。

## 一段階の詳細

| 項目 | 表示する内容の例 |
| --- | --- |
| 現在位置 | API側の「ジョブ登録」。全体図でも同じ識別子を強調 |
| 入力 | 保存済み注文のID（教材値 `order-17`） |
| 処理 | `queue.add({ orderId })`。該当ソースと根拠の種類を添える |
| 出力 | キューがジョブを受け付けたこと。配送の完了とは区別 |
| 次の動き | API側は受付応答へ、ワーカー側は受信後に処理 |
| 未確認 | 登録失敗時の扱いは仕様にないため、実装を調べるまで未確認 |

点の移動を「注文IDの受け渡し」、輪郭の強調を「処理中」、ラベルの更新を「確認できる状態変化」として使う。待機時間は説明用であり実測値ではない。過去の段階へ移動したら、その時点の教材状態へ戻す。

## HTMLの構成

1. 対象の利用場面、入力例、調べた範囲、根拠の種類。
2. 全体のフロー図と、再生・停止・段階選択。必要な分岐と外部境界。
3. 選択段階の入力・処理・出力・ソース。全体図との往復。
4. 「注文保存が失敗したら、どこまで進むか」の予想と、選択後の解説。

この順を基本とし、短いフローでは画面や操作を増やしすぎない。主経路と重要な例外を先に扱い、全分岐を網羅することを目的にしない。
